### Task 1 — Prerequisites gate

**This task can hard-block the phase. Do it first and do not proceed on assumptions.**

Add the Spring AI pgvector starter (`spring-ai-starter-vector-store-pgvector`, version managed by the existing BOM). Then verify against the live Supabase instance what the spec's Database prerequisites section describes: whether `vector`, `hstore` and `uuid-ossp` can actually be created by the connecting role, and whether `uuid_generate_v4()` resolves on the pooler connection's `search_path`.

As of 2026-08-14 `vector` and `hstore` were **not installed** and the role is **not superuser** — so this is a real question, not a formality. The database is shared with `tapas-fpl-app`: creating extensions there is a decision to raise with the project owner, not a side effect to slip in. If automatic creation is not available, take the spec's documented fallback (enable via Supabase dashboard, `initialize-schema: false`, hand-written DDL) and record which path was taken.

Also update `AGENTS.md`, `docs/DEVELOPMENT.md` and `docs/STATUS.md` to state that `OPENAI_API_KEY` is mandatory in every deployment regardless of `SPRING_AI_PROVIDER`. (`backend/.env.test.example` already carries the key — the gap is in the prose docs.)

**Done when:** the dependency resolves; you can state with evidence whether schema auto-init will work or the fallback is needed; the docs no longer let a reader assume the OpenAI key is optional.

### Task 2 — Vector store wiring

Apply the spec's Configuration table in full — every row, explicitly. Get a working `VectorStore` bean backed by `fpl_embeddings`.

Two failure modes to actively check rather than assume away: the application must start with `SPRING_AI_PROVIDER=anthropic` and a *populated* OpenAI key (the embedding autoconfiguration activates independently of the chat provider), and startup must not make a live OpenAI call to resolve dimensions.

**Done when:** `fpl_embeddings` exists in Supabase with the expected shape after a run; the app starts cleanly under both provider settings; the full existing Phase 1 test suite still passes with the starter on the classpath.

> **Landed 2026-08-14:** `schema-validation: true` cannot be combined with `initialize-schema: true` — see the spec's Configuration table, revised after discovering this against the real bytecode. Left off; `initialize-schema` alone is sufficient and idempotent.

### Task 3 — Ingestion

Move the seven documents to `backend/src/main/resources/docs/` (fixed by the spec — the Dockerfile only copies `backend/`) and add the front matter the spec's Document metadata section requires; all seven are `kind: reference` for the 2026/27 season. Build the ingestion runner: section-based markdown chunking with the header prefixed into each chunk body, front matter carried into chunk metadata, embedding via OpenAI, writing to the store, gated behind an explicit flag, deleting existing rows first, terminating the process when done. A document missing front matter must fail ingestion loudly rather than land in the store undated.

The corpus is expected to grow by several documents a week during the season, including dated news and opinion pieces — so treat the metadata path as load-bearing, not decoration, and keep ingestion runnable by whoever adds documents without needing to understand the internals.

Tests belong to this task. They must run against the isolated test table the spec requires — verify that isolation is real before writing anything else, because getting it wrong destroys the production corpus on the next `./gradlew test`.

**Done when:** ingestion against real Supabase populates `fpl_embeddings` from the current documents with metadata intact; a document lacking front matter fails the run; re-running after editing a document reflects the edit without duplicating rows; the process exits; tests cover ingestion mechanics against the fixture corpus and demonstrably never touch `fpl_embeddings`.

### Task 4 — The `searchStrategyDocs` tool

Build the tool to the spec's requirements: expiry filtering at query time (`SearchRequest.filterExpression`, so expired `timely` documents never reach the model), per-chunk attribution carrying `kind` and the validity window, a distinguishable empty-store response, and a description scoping it to advice questions. Register via `FplTool`. Amend `AGENTS.md`'s "every tool prefixes its reply with `SeasonContext.provenance()`" convention in this same task so the codebase and its documented conventions don't contradict each other.

Tests belong to this task: retrieval of expected fixture content, the empty-store path, the error path, and — using fixture documents with deliberately past `valid_until` dates — that expired content is excluded while unexpired and no-expiry content is returned. That last one is the case that silently rots in production if nobody pins it now.

**Done when:** the tool returns relevant chunks for strategy-shaped queries against real ingested data; expired fixtures are provably excluded; the empty-store and error paths return their intended strings rather than throwing; `AGENTS.md` matches what the code does.

> **Review checkpoint.** Request a code review of Tasks 1–4 before wiring anything into the prompt. Apply findings before continuing.

### Task 5 — System prompt

Add the advice-question instruction: stats tool *and* `searchStrategyDocs` together for advice-shaped questions, phrased to accommodate a future squad-aware tool without a rewrite (spec explains the shape; its example is not a required sentence). Add the companion instruction on retrieved-content age: weigh `timely` documents by how old they are and say so when citing something from weeks back — the mirror of the existing seasonal-provenance instruction, for the same reason.

**Done when:** both instructions sit coherently alongside the existing provenance and rules sections in `system-prompt.st`.

### Task 6 — Retrieval quality baseline

Write down ~8 real questions paired with the document each should retrieve (the spec gives three examples to start from). Run them against the real corpus. Record actual versus expected in `docs/STATUS.md`.

This is the task that catches chunking problems — misattributed chip advice, severed tables, sections retrieved without their context. Fixture-based unit tests structurally cannot. If results are poor, the fix is chunking or top-k, and that decision belongs here rather than after deploy.

**Done when:** all ~8 questions retrieve from the expected document, or the misses are understood and either fixed or recorded in `STATUS.md` with reasoning.

### Task 7 — End-to-end verification

Through the real chat flow, not mocks: ask a genuine advice question and confirm both a stats tool and `searchStrategyDocs` fire and the answer visibly draws on retrieved content. Ask a pure stat question and confirm `searchStrategyDocs` is **not** called — the negative case is the one that proves the tool-based design works as intended.

Update `docs/STATUS.md` with what was built, deviations, and anything the spec failed to anticipate, in the same detail Phase 1 maintained.

**Done when:** both question types behave as the spec describes, verified against the running application.
