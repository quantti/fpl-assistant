# FPL Assistant — Phase 2: RAG Implementation Plan

**Spec:** `docs/superpowers/specs/2026-08-14-phase2-rag-design.md` — read it first. This plan is deliberately high-level: it names what each task must accomplish and which existing conventions it must follow, not the code that accomplishes it. The implementing agent chooses class shapes, method signatures, exact wording, and test structure; only the spec's stated constraints are binding.

**PROGRESS:** Task 0/7 done

**Conventions that apply to every task below**, established in Phase 1 and not repeated per-task: query Supabase via the same credential/pooler setup in `docs/DEVELOPMENT.md`; new tools implement `FplTool` and follow the `DataAccessException`-caught / logged / error-string-returned pattern; commit after each task; update this file's `PROGRESS` line and `docs/STATUS.md` as you go, the same way Phase 1 did.

---

### Task 1 — Dependencies, secrets, and DB readiness

Add whatever Spring AI pgvector starter dependency the current Spring AI 2.0.x release provides. Confirm the `pgvector` extension is enabled on the shared Supabase project (it may already be, given `tapas-fpl-app` shares the instance — check before assuming). Update `AGENTS.md` and `docs/DEVELOPMENT.md`/`STATUS.md` to state plainly that `OPENAI_API_KEY` is now a mandatory secret for every deployment regardless of `SPRING_AI_PROVIDER`, per the spec's reasoning (Anthropic has no embeddings API).

**Done when:** the build resolves the new dependency, and the docs no longer let a future reader assume the OpenAI key is optional.

### Task 2 — Vector store wiring

Build the `RagConfig` (or equivalently named) piece that gives the application a working `VectorStore` bean backed by Supabase's `fpl_embeddings` table, using Spring AI's `PgVectorStore` abstraction per the spec. Confirm the table gets created (schema-managed by the store, not hand-written DDL) against the real Supabase instance.

**Done when:** the application starts with the bean present and `fpl_embeddings` exists in Supabase after a run.

### Task 3 — Ingestion

Get the seven files currently in the repo-root `strategy_docs/` onto the backend's classpath where an ingestion process can read them (the spec leaves the exact mechanism — move, copy, or resource-path addition — to you). Build the ingestion runner: reads the docs, chunks them, embeds via OpenAI, writes to the vector store, gated behind an explicit flag so it never runs during normal startup. Truncate-and-reload semantics on each run, per the spec — no dedup logic.

**Done when:** running the ingestion command against real Supabase populates `fpl_embeddings` from the current `strategy_docs/` content, and running it again after an edit reflects the edit rather than duplicating rows.

### Task 4 — The `searchStrategyDocs` tool

Build the tool per the spec: free-text query in, top-k formatted chunks out, no season-provenance prefix, tool description stating when the model should reach for it (advice/transfer/captaincy/chip questions, not stat lookups), registered via `FplTool` so it joins the existing collection with no `ChatService` changes.

**Done when:** calling the tool directly against real ingested data for a strategy-shaped query returns relevant chunks, and for something nonsensical returns a sane empty/error response rather than throwing.

### Task 5 — System prompt

Add the advice-question instruction: use a stats tool *and* `searchStrategyDocs` together for advice-shaped questions. Phrase it so it already accommodates a future squad-aware tool without needing a rewrite in Phase 5 (spec explains why and gives an example shape — don't treat the example as the required exact sentence).

**Done when:** the instruction is in `system-prompt.st` and reads coherently alongside the existing seasonal-provenance and rules sections.

### Task 6 — Tests

Add a small fixture doc set (not the real `strategy_docs/` corpus) for ingestion/retrieval tests, per the spec's reasoning — tests shouldn't depend on content that changes independently of code. Cover: ingestion populates the store correctly, `searchStrategyDocs` retrieves the expected fixture content for a matching query, and the tool's error path behaves like the rest of the codebase's tools. Run the full existing suite to confirm nothing in Phase 1's tools regressed.

**Done when:** the new tests pass against live Supabase and the full suite is green.

### Task 7 — End-to-end verification and docs

Run real ingestion against the actual `strategy_docs/` corpus. Start the app, ask it a genuine advice question ("who should I captain this week", "should I use my wildcard now") through the real chat flow, and confirm both a stats tool and `searchStrategyDocs` fire and the answer visibly draws on retrieved strategy content. Ask a pure stat question and confirm `searchStrategyDocs` is *not* called. Update `docs/STATUS.md` with what was built, any deviations, and anything discovered that the spec didn't anticipate — same discipline Phase 1's `STATUS.md` maintained throughout.

**Done when:** both question types behave as the spec describes, against the real backend, not a mock.
