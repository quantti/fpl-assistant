## Proposed actual STAGING test — requires separate owner approval

This is a **runbook, not authorization or a scheduled activation**. Do not run it in this implementation session. A successful synthetic test or green PR does not prove monthly database egress, a GW5 backfill or ACTIVE readiness. Keep the fixed two-worker HTTP budget and the Tapas single-writer fence unchanged. Run only on the merged, successfully deployed commit, initially OFF; no manual Fly deploy, ACTIVE mode, Tapas writer change, schema reset, deletion of request-attempt evidence, or session `SET` through the transaction pooler.

**Preflight, with owner present:** Recreate and locally dry-run the independent observer/rollback guard first; the previous raw guard lived in a temporary private directory, not a reusable checked-in harness. Confirm the deployed SHA and health; a fresh SELECT-only inspection of durable OFF mode/epoch, zero PENDING/LEASED runs, zero unresolved `fpl_sync_request_attempt` rows (`completed_at IS NULL`), published-receipt fingerprint, evidence/VERIFIED/GW5 counts and database size. If an unresolved attempt exists, stop for manual outcome reconciliation; TTL is not a refund. Obtain the current Supabase organisation egress/DB-size dashboard readings and an agreed budget for this billing period. Verify the read-only DB-socket observer against a held 524,288-byte loopback transfer, including port/cookie selection, missing samples and sampler failure. Verify the independent rollback supervisor can request OFF and check durable OFF/health, and that the owner has Fly-console fallback. If any preflight/guard cannot be proven, do not start STAGING.

**Arm the rollback guard before requesting STAGING.** Limit one attended epoch to the earliest of 10 minutes from the mode request, 15,000,000 observed PostgreSQL TCP RX bytes, or 20,000,000 whole-machine RX bytes (same conservative limits as the 27 September retest). Also stop on explicit owner request, guard/controller exit, missing or stale telemetry, changed machine boot, runtime error, or guest available memory below 192 MiB; allow at most 90 seconds startup-health grace. The traffic limits are stop *triggers*, not hard caps: sampling and OFF replacement can overshoot. Do not raise them merely to obtain a staged fixture.

**Observe, without extra body reads:** Timestamp STAGING activation, first and total *durable admissions* in `fpl_sync_request_attempt`, staged payload rows by endpoint/validation state (including explicit HTTP 429 errors), first completed VALID player history, distinct completed histories, first fixture reaching STAGED and its required-history evidence, persisted run deferral reasons (especially UNSETTLED), peak incomplete fixture pairs, memory minimum and throughput until stop. Admission is not proof a GET reached FPL; FPL-server-observed GET counts and raw Retry-After headers are unavailable from production storage. Report persisted cooldown deadlines and any explicitly staged HTTP 429 errors instead, and explicitly mark any uncertain response whose header is unknown. Take before/after SELECT-only `pg_stat_statements` snapshots without resetting shared statistics; report calls, returned rows and raw-body read families separately from the socket counter. The DB counter includes startup/TLS/protocol, can miss short-lived sockets and is not Supabase billed egress; HTTP/staged source lengths are not DB RX. If no history completes in the first 90 seconds of healthy STAGING, stop early and diagnose, even if neither traffic cap has fired. If a 429 or an unresolved permit appears, stop and preserve its persisted evidence; do not force additional attempts.

**Rollback and acceptance:** Request OFF at the first trigger or the ten-minute limit; verify OFF **in the database**, a later fenced epoch with zero active runs, normal public health UP, unchanged publication-receipt fingerprint and core/evidence/GW5 counts, and no new unfinished request attempt. If any differ, treat it as a failed rollback/incident and do not restore Tapas or retry STAGING automatically. Record stop time and post-stop traffic sample, but do not claim exact billed totals. Compare first-history/completed-history and fixture-STAGED progress with the 27 September zero-history/zero-fixture result, while recording any traffic cap hit honestly. A first history and a STAGED fixture before the caps would establish bounded progress for this epoch only; missing either is a failed progress gate, not permission to extend the run. Even if both occur, sustained idle/matchday egress and ACTIVE publication remain separate approvals, with a provider-dashboard follow-up when billing catches up.
