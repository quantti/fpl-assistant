## Confirmed blockers

1. **P1 — Tapas row proof and grants.** `tapas-fpl-app/backend/app/services/pfs_read.py:29–115` only checks `fpl_fixture_sync` VERIFIED/current generation and its evidence. It neither joins `fpl_player_fixture_current` nor validates the new page receipt/physical fingerprint. For a new-only GW7 fixture with no old observation (all ten are currently in that state), it treats a new provisional physical PFS row as unowned legacy and exposes points and default-valued optional metrics without the new proof/mask. For a previously owned fixture with revoked verification it withholds even good new provisional rows. Tapas `history.py` and `set_and_forget.py` consume this projection. In production, `tapas_runtime` has SELECT on `fpl_fixture_sync` and old evidence, but **no SELECT** on `fpl_player_fixture_current`, `fpl_sync_receipt` or `fpl_gameweek_stat_sync`. Repair the reader and narrowly grant required new SELECT privileges before switching; prove unknown/withdrawn/stale/partial rows cannot become zero or legacy fallback. Source: assistant `PfsReadSource.cte()` and `IncrementalPfsRepository.revokeObsoleteFixtureVerification`.
2. **P1 — no safe existing ACTIVE-to-importer handoff.** `OwnedMatchdayRuntime.stop()` calls `PlannerRuntimeRepository.deactivate`, which fences pending/leased runs and changes the persisted mode to OFF with a new epoch. `CoalescedPlayerHistoryImportConfiguration.existingActiveFence` requires an **already ACTIVE** persisted epoch and deliberately never activates one; startup otherwise fails. Retaining the old ACTIVE row by skipping drain or relying on a failed shutdown risks concurrent writers. Provide and rehearse a reviewed operator-controlled transition after the old process/DB operations have drained: mint a new ACTIVE epoch with the old writer absent and new writer still inert, then start the importer. No direct ad-hoc update, old process crash, overlapping Fly machines or silent activation on app boot.
3. **P1 — fixture incidents cannot recover under the new verifier.** The importer watchdog skips legacy fixture checks, but `OwnedSyncWatchdog.recoveryEvidence` / `verifiedRecovery` requires `fpl_fixture_sync.state=VERIFIED` with current verified generation to recover old fixture incidents. The new path does not make new fixtures legacy VERIFIED. Eighteen current open fixture incidents can therefore hold the external monitor DOWN indefinitely even after valid new-path recovery. Introduce a separately reviewed, **proof-based** migration/recovery signal (or explicitly accept an unresolved DOWN while coverage is genuinely absent); do not erase or falsely mark alerts delivered/recovered. Confirm real end-to-end notification and incident recovery.
4. **P1 — Tapas Points Against completeness.** `scripts/scheduled_update.py:674–746` forms a team-side sum from whichever `pfs_read` rows exist, and checks two aggregate sides per finished fixture, not a source-backed full set of positive appearances. Simply teaching `pfs_read` to accept provisional rows would permit understated derived totals when only some players of both clubs have arrived. Preserve the last published derived value until a complete current fixture-side manifest is proven; cover an omitted positive participant, optional NULL and a double gameweek in tests. Tapas' raw row-count status field is not a completeness proof.
5. **Operational no-go today.** GW6 is still unchecked/unfinished in stored source, with zero PFS rows and 19 open incidents. The shared 5,000-per-rolling-day HTTP budget is exhausted and 59 old runs are pending. First new importer cycle runs immediately and may be budget-deferred. Real full-league body cost, sustained egress, first-matchday latency, monitoring and single-writer rollback are not production-proven. Green CI verifies code, not these live gates. Existing `docs/OWNED-SYNC-OPERATIONS.md` begins with an older OFF83 snapshot; the live ACTIVE94 snapshot must govern the decision.
